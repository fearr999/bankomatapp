# Настройка Google Sheets (база данных)

## 1. Создайте таблицу
Создайте новую Google Таблицу (sheets.new) и переименуйте её, например,
`Merchandiser_DB`. Внутри создайте листы (вкладки) с ТОЧНО такими названиями
и заголовками в первой строке (регистр важен — backend ищет по этим именам):

### Лист `Users`
| User_ID | Name | Role | PIN | Phone | Status |
|---|---|---|---|---|---|
| U001 | Иван Иванов | Worker | 1234 | +998901234567 | Active |
| U002 | Админ Админов | Admin | 9999 | +998907654321 | Active |

- `Role` — строго `Worker` или `Admin`.
- `PIN` — 4-6 цифр, ваш экран логина спрашивает именно его.

### Лист `Businesses` (мультибизнес — какие сферы доступны в приложении)
| Business_ID | Name | Icon | Color | Task_Mode | Checklist_Schema_JSON |
|---|---|---|---|---|---|
| merch | Мерчендайзинг | 🛒 | #3F51B5 | daily | `[]` |
| atm_cleaning | Обслуживание банкоматов | 🏧 | #009688 | cycle | (см. пример ниже) |

- `Business_ID` — короткий латинский код, используется в приложении как ключ.
- `Icon` — один эмодзи, показывается на карточке выбора бизнеса.
- `Color` — HEX-цвет темы приложения для этого бизнеса (`#RRGGBB`).
- `Task_Mode` — **daily** (по умолчанию, как раньше) или **cycle**:
  - `daily` — задачи берутся из листа `Tasks`, нужно вручную добавлять
    строку на каждую точку на каждый день (подходит для мерча — там
    посещения не циклические, а по расписанию).
  - `cycle` — задачи вообще не берутся из `Tasks`. Вместо этого устройство
    закрепляется за работником один раз в листе `Stores` (колонка
    `Assigned_User_ID`), и приложение само показывает всё, что этот
    работник ещё не закрыл в текущем цикле. Как только закрыто всё —
    цикл автоматически обнуляется, и список снова полон. То, что раньше
    называлось "бригада А/Б/В" — это просто разные `Assigned_User_ID`
    (разные PIN-логины) для устройств одного бизнеса. Именно этот режим
    нужен банкоматам, где 100+ устройств на бригаду и заполнять `Tasks`
    руками каждый день нереально.
- `Checklist_Schema_JSON` — JSON-массив полей чек-листа, который увидит
  работник на объекте (кроме `merch` — у него отдельный экран учёта SKU,
  для него оставьте `[]`). Пример для `atm_cleaning`:
  ```json
  [
    {"id":"exterior_clean","label":"Внешняя чистка корпуса","type":"checkbox","required":true},
    {"id":"card_reader_clean","label":"Чистка картоприёмника","type":"checkbox","required":true},
    {"id":"cash_dispenser_clean","label":"Чистка купюроприёмника/диспенсера","type":"checkbox","required":true},
    {"id":"receipt_printer_ok","label":"Принтер чеков (бумага/печать) в порядке","type":"checkbox","required":true},
    {"id":"screen_clean","label":"Чистка экрана и клавиатуры","type":"checkbox","required":true},
    {"id":"trash_removed","label":"Вывезен мусор/чеки из корзины","type":"checkbox","required":false},
    {"id":"issues_found","label":"Обнаружены неисправности","type":"checkbox","required":false},
    {"id":"comment","label":"Комментарий / что обнаружено","type":"text","required":false}
  ]
  ```
  Поддерживаемые `type`: `checkbox` (да/нет), `text` (короткий текст),
  `number` (число). Вставляйте JSON в ячейку одной строкой без переносов.

### Лист `Stores` (точки — магазины ИЛИ банкоматы ИЛИ любой другой объект)
| Store_ID | Business_ID | Name | Address | Latitude | Longitude | Allowed_Radius_Meters | Assigned_User_ID |
|---|---|---|---|---|---|---|---|
| S001 | merch | Магазин "Радуга" | г. Ташкент, ул. Примерная 1 | 41.311081 | 69.240562 | 100 | |
| ATM001 | atm_cleaning | Банкомат ТЦ "Мега" | г. Ташкент, пр. Мега 5 | 41.320000 | 69.250000 | 50 | U010 |

- Добавьте колонку `Business_ID` в существующий лист `Stores` (если у вас уже
  есть старые строки без неё — приложение по умолчанию считает их `merch`,
  можно оставить как есть или проставить явно).
- Координаты возьмите из Google Maps (ПКМ по точке на карте -> координаты копируются в буфер).
- `Assigned_User_ID` — **обязательна для бизнесов с `Task_Mode = cycle`**
  (например банкоматы). Впишите туда `User_ID` работника (PIN-логина),
  за которым закреплено это устройство — обычно это и есть "бригада".
  Заполняется один раз, а не каждый день. Для `daily`-бизнесов (мерч)
  эту колонку можно оставить пустой — там распределение идёт через `Tasks`.

### Лист `Cycles` (только для бизнесов с `Task_Mode = cycle`)
Создавать не обязательно — backend создаст его сам при первом запросе,
с заголовками: `User_ID | Business_ID | Cycle_Number | Cycle_Start_Date`.
Раз в цикл (или если нужно сбросить прогресс досрочно) можно просто
поправить `Cycle_Start_Date` на эту дату вручную — старые визиты раньше
этой даты в подсчёт входить перестанут.

### Лист `Products`
| Product_ID | Category | SKU_Name | Barcode | Price |
|---|---|---|---|---|
| P001 | Напитки | Coca-Cola 0.5л | 4870... | 12000 |

### Лист `Tasks` (только для бизнесов с `Task_Mode = daily`, например мерч)
| Task_ID | User_ID | Store_ID | Scheduled_Date | Status |
|---|---|---|---|---|
| T001 | U001 | S001 | 2026-07-27 | Pending |

- `Scheduled_Date` — формат `YYYY-MM-DD`, сравнивается с сегодняшней датой сервера.
- Бизнес задачи определяется автоматически по `Store_ID -> Stores.Business_ID`,
  отдельно проставлять его в `Tasks` не нужно.
- Это единственный лист, который вам нужно будет заполнять каждый день/неделю
  вручную (или писать отдельный скрипт-планировщик — не входит в MVP).
- Для `cycle`-бизнесов (банкоматы) этот лист вообще не используется —
  список формируется сам из `Stores.Assigned_User_ID` + `Cycles`, см. выше.

### Лист `Visits_Log`
| Log_ID | User_ID | Store_ID | CheckIn_Time | CheckOut_Time | CheckIn_Lat | CheckIn_Long | Distance_Error_Meters | Status |
|---|---|---|---|---|---|---|---|---|

Оставьте пустым — backend заполняет автоматически.

### Лист `Report_Details` (только для бизнеса `merch`)
| Report_ID | Log_ID | Product_ID | Is_Available | Stock_Qty | Facing_Qty | Actual_Price |
|---|---|---|---|---|---|---|

Оставьте пустым.

### Лист `Checklist_Reports` (для остальных бизнесов, например `atm_cleaning`)
Создавать не обязательно — backend создаст его сам при первой отправке
чек-листа, с заголовками:
`Report_ID | Log_ID | Business_ID | Payload_JSON | Timestamp`

### Лист `Photos`
| Photo_ID | Log_ID | Type | Drive_File_URL | Timestamp |
|---|---|---|---|---|

Оставьте пустым.

### Лист `Sessions`
Создавать не обязательно — backend создаст его сам при первом логине.
Но если хотите — создайте с заголовками:
`Token | User_ID | Created_At | Expires_At`

## 2. Подключите Apps Script
1. В таблице: `Расширения -> Apps Script`.
2. Удалите содержимое `Code.gs` по умолчанию, вставьте содержимое файла
   `backend/Code.gs` из этого проекта.
3. `Настройки проекта (шестерёнка слева) -> Свойства скрипта (Script Properties)`,
   добавьте:
   - `API_KEY` = придумайте длинную случайную строку (например, сгенерируйте на
     https://www.uuidgenerator.net/) — впишите ТУ ЖЕ строку в
     `lib/config/app_config.dart -> apiKey`.
   - `DRIVE_FOLDER_ID` = создайте папку на Google Drive для фото, откройте её,
     скопируйте ID из URL (после `/folders/`).
4. `Deploy -> New deployment -> Select type: Web app`:
   - Execute as: **Me**
   - Who has access: **Anyone**
5. Нажмите Deploy, скопируйте выданный URL (`.../exec`) —
   впишите его в `lib/config/app_config.dart -> apiBaseUrl`.

## 3. Быстрая проверка backend без приложения
Можно проверить, что backend вообще работает, через `curl` (замените URL и ключ):

```bash
curl -X POST "ВАШ_URL_/exec" \
  -H "Content-Type: application/json" \
  -d '{"action":"login","pin":"1234","apiKey":"ВАШ_API_KEY"}'
```

Ожидаемый ответ: `{"status":"success","token":"...","userId":"U001",...}`.

## 4. Про квоты (актуально на июль 2026)
Для теста на 2-5 человек вы используете это в разы меньше лимитов:
- URL Fetch / вызовы Web App: 20 000/день на обычный аккаунт — вы даже близко
  не подойдёте при 2-5 пользователях с несколькими визитами в день.
- POST-запрос — до 50 МБ, сжатое фото ~200-400 КБ, тоже с большим запасом.
- Каждое выполнение скрипта ограничено 6 минутами — при таком объёме данных
  все функции отрабатывают за доли секунды.

Если позже команда вырастет за 20-30 человек с фоновым геотрекингом —
тогда стоит переносить `Visits_Log`/`Report_Details`/`Photos` в Firebase
(см. обсуждение архитектуры выше в переписке).
